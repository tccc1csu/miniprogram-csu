# CloudBase HTTPS 事务契约（实施修订）

2026-11-26 用户授权改代码，要求电脑关闭仍运行。HTTP 并无跨请求的 PostgreSQL 连接事务。为避免重写全部业务逻辑造成规则漂移，采用后端事务工作副本 + 云端版本比较提交。

## 数据与信任边界

- `youth_workbench` 下 38 张表是唯一权威关系数据，保留外键、唯一约束、工时整数与不可变封存模型。私有 bucket 保存附件字节。
- 容器内 PGlite 只是在内存中执行既有服务端业务 SQL 的临时工作副本，不持久化、不作为断网降级来源。云库不可用则业务不可用。Web / 小程序仍只访问 `/api/v1`。
- 固定 RPC：`wb_snapshot`、`wb_command`、`wb_upload`、`wb_upload_orphans`。只授权 service_role，撤销 PUBLIC/anon/authenticated。没有传入 SQL 文本的入口；写入目标限于固定表清单，列及主键从数据库目录取得。

## 原子业务命令

1. 一致快照一次性返回 revision 与所有业务行；STABLE 函数内所有读取共享同一 MVCC 快照。
2. 既有业务函数在容器的内存 SQL 事务执行身份、部门、阶段、版本和计费校验，触发器按顺序捕获行变更。副作用（上传、消息发送）不得放进可重试业务回调。
3. `wb_command(request_id,digest,expected_revision,changes,result,auth)` 在单个 PG 事务锁定 `_state`，重新核验会话、有效账号、角色和部门，再检查版本，应用所有行变更及去重记录，一次提交。
4. 版本变化则不写数据，后端重新取快照并重新执行完整业务函数（最多 8 次）。任何约束失败整体回滚。派发和轮值游标、审核和下一条通知、完成和归档和工时全部同时提交。
5. 同一次网络重试始终使用相同 id、摘要和内容。已提交时返回存储结果；不同摘要复用 id 拒绝。API 跨请求的重复完成另由既有业务幂等逻辑处理。

该设计对所有业务写入按全局 revision 排序，适合学校组织当前规模。每个请求仅检查一次新版本，未变化不下载数据。数据增长后可按任务/报表分区快照与 revision；在此之前不得宣称无限规模，需监测快照体积与冲突重试。

## 附件、调度和错误

- 上传：云端 prepare → 私有存储写字节 → 业务命令确认 files 元数据 → complete。失败或丢失响应保留可对账状态；定时任务清理一小时以上且无 files 引用的孤立对象。下载先验证业务权限，再从云存储取字节，校验大小/SHA256。
- 每分钟云事件函数调用带独立令牌的内部调度 API，能唤醒缩容服务。提醒有唯一键，消息有领取租约、幂等 id 和退避重试。未配置微信机器人不报发送成功。
- 健康检查实际访问云库，只公开 ready/provider，不暴露内部连接、凭据和错误堆栈。
- 迁移用版本 SQL；旧小程序生产集合仅只读核对，不自动导入演示数据。
