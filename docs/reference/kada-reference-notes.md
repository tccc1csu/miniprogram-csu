# KADA Cooperative System 参考记录

这份记录区分“参考项目文档中的表达方式”和“本项目自己的业务内容”。参考仓库为 `firzanabadrus/sistem-koperasi-kada`，本地材料包括 SRS Documentation、SDD Documentation 和 STD Documentation。

## 1. SRS 的可借鉴结构

- 引言：目的、范围、术语、参考资料、文档概览。
- 特定需求：角色/Persona、系统用例图、状态图、用户故事或用例细节、功能与非功能要求、设计约束。
- 每个关键用例给出正常场景、异常场景和相应的交互图。
- 需求面向项目经理、开发者、测试者和业务角色，强调可追踪和可验证。

本项目保留“目的、范围、角色、功能/质量需求、约束、追踪”的结构，但把 KADA 的会员、贷款、财务报表替换为青年传媒中心的工作记录、跨部门协同、摄制预约、周报和津贴规则。

## 2. SDD 的可借鉴结构

- 用例视图：系统和外部执行者的交互。
- 逻辑视图：核心类或领域结构。
- 过程视图：关键用例的序列和状态。
- 数据设计：实体、字段、约束和关系。
- 用户界面设计：按用例说明界面支持的业务价值。
- 架构、接口和设计约束应能追溯回 SRS。

本项目当前处在课程 A（业务建模）和 B（需求）阶段，所以先固定愿景、业务边界、用例和需求语言；类图、分析序列图、数据层和界面精化留到 C/D 阶段，避免把设计提前冒充需求。

## 3. STD 的可借鉴结构

- 测试目标和范围。
- 测试策略和环境/数据。
- 按模块或用例组织测试套件。
- 每条测试用例包含前置数据、步骤、输入、预期结果、实际结果和通过状态。
- 非功能测试覆盖性能、安全、可靠性、可用性和兼容性。
- 需求追踪矩阵把需求、设计、测试和发布门槛串起来。

本项目继续使用 `STD-framework.md` 的测试套件编号，但测试用例必须从本轮系统用例规约和业务规则派生，而不是复制 KADA 的测试数据。

## 4. 课程 PPT 对文档结构的修正

参考仓库把“用户故事 + 活动图 + 系统序列图”作为主要需求表达，这适合其课程作业；本案例严格按课程 PPT 的 A→B 工作流补齐：

1. 愿景：目标组织代表关心的组织指标和改进值。
2. 业务用例图：组织为外部参与者提供的业务价值集合。
3. 现状业务序列图：未引入目标系统时真实发生的跨人/跨工具协作。
4. 改进业务序列图：目标系统介入后仍由业务人员承担的判断责任，以及系统承担的记录、通知、状态和核算责任。
5. 系统用例图：从改进业务序列映射出系统对外提供的可接受价值。
6. 系统用例规约：前置、后置、涉众利益、基本/扩展路径、字段列表、业务规则、质量需求和设计约束。

因此，KADA 的文档结构可以参考，业务名词、参与者、流程和数据必须以青年传媒中心实际项目为准。
