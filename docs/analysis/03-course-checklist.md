# 课程工件评审清单（编写说明）

本文件供修订检查，不作为作业正文。页码按课程 PDF 物理页计。

| 工件 | 课程要求与本轮检查重点 |
| --- | --- |
| 愿景 | 第 33 页七项表：系统、目标组织、老大、目标、度量指标、对比时间、改进值。写组织收益，不写功能清单；基线与目标不混淆。 |
| 业务用例图 | 第 86 页：执行者在业务责任边界外，是人群或机构；用例是组织提供的价值。不要把内部员工和沟通工具一律画成外部业务执行者。 |
| 业务序列图图例 | 第 87 页：圆内小人为业务工人，空圆带斜线为业务实体。第 89 页：新增目标系统是新的业务实体。 |
| 现状序列图 | 依据已知实际流程，不虚构人员或审批节点；通信载体与业务责任分开，不同频率的业务分开。 |
| 消息与责任 | 第 108 页：A 请求 B 做某事；每个实线动词逐条读成“接收者执行该动作”。结果用虚线返回，自消息允许表达该对象自身责任。 |
| 改进序列图 | 明确派发、执行、审核、归档各环节责任；冲突拒绝在创建前，退回后重新审核，统计结果可追溯。 |
| 系统用例图 | 从外部指向目标软件的责任请求映射用例；区分软件、人类执行者、外部辅助系统；核心用例按主要职责拆分。 |
| 用例规约 | 保留涉众利益、前后置条件、基本／扩展路径、业务字段、规则和必要质量约束。执行者一次提交完整业务信息，系统验证和处理；不写界面、组件或实现。 |
| 跨工件一致性 | 同名同责；图中用例编号对应规约；摄制归档归指定办公部成员；明细与周汇总两层结构保持一致。 |

一用例一个主要责任角色是本项目的职责划分目标，不是“所有 UML 用例只能有一名执行者”的通用语法限制。公共身份验证、真实辅助参与允许共享，不为减少连线删掉实际责任。


## 2026-10-09 增补检查

- 新增外部门服务需求、六部门职责、运营一审与老师二审；不类推未知部门的一审岗位。
- 通用流转使用美编设计到运营推文的具体实例，区分阶段确认与稿件审核，退回后不能继续进入下一节点。
- 部长派发与摄制抢单不可产生两个当前承接人；归档与周报不得重复应用同一加急系数。
- 稿件截止日期为可选；中心周报主要执行者为办公部部长。
- 原型截图与访谈人工现状标明各自来源时期；图与规约不等于软件已实现或已经验收。
- 图源所列每个用例均有规约，20 份规约全部保留触发、前后置条件、涉众利益和基本／扩展路径；3 个系统视图合计 19 个核心用例，登录为公共支撑。
