## A 业务建模

## A.1 项目愿景

青年传媒中心工作台将分散于微信群、稿件链接和人工表格中的协作沉淀到可追溯任务，通过网页管理与手机办理，让完成即归档、贡献可核验、结算有依据。

| 愿景要素 | 定义 |
| --- | --- |
| 系统 | 青年传媒中心工作台 |
| 目标组织 | 学校青年传媒中心及其办公、采编、运营、摄制、美编、原创六部门 |
| 组织负责人 | 指导老师与中心管理团队 |
| 业务目标 | 降低人工收集核对工时的耗时，并减少任务、版本、审核及附件的散失 |
| 度量指标 | 同等任务量下办公部每周收集、核对、汇总所用总人时；完成任务的可追溯归档比例 |
| 对比基线 | 历史访谈估计人工统计约60分钟/周，尚非实测；改造前群聊、材料和表格相互分离 |
| 改进目标 | 通过试运行对比统计耗时，正常完成任务均保留归档与贡献依据；实际下降幅度待同口径测量 |

目前实现覆盖任务办理和结算证据，不能把自动化测试通过等同于人工统计耗时已经下降。验收示例数据用于演示角色和流程，不是真实历史财务记录。

## A.2 业务建模与 B 需求形成

### 组织边界、业务执行者与涉众

业务边界是整个青年传媒中心。校内其他组织或活动需求方从边界外提出宣传、拍摄或设计需求，结算核对方关注可信工作量结果。中心内部的部长、干事和指导老师作为业务工人在序列中协作；他们操作软件时，又是软件边界外的系统参与者。业务执行者与系统参与者不能混用。

图形约定：业务序列使用PlantUML自定义业务工人（带斜线的人形圆标）和业务实体（带斜线的圆标）；任务档案、稿件清单、工时台账是业务实体。图中的记录操作由改进后的工作台支持，软件整体不充当业务实体。系统序列与分析序列另采用软件边界及BCE符号。

| 部门 | 核心工作 | 跨部门联系 |
| --- | --- | --- |
| 办公部 | 稿件对接、活动工作、工时核对及封存 | 与采编逐稿逐站点对接，与全中心结算 |
| 采编部 | 稿件内容、原创作者、源稿内容审核 | 给办公交付；外部来稿排版前审核 |
| 运营部 | 排版、内部审校、协调教师两审与发布 | 消化已归档稿件及外部来稿 |
| 摄制部 | 预约、承接、交付、验收 | 为活动方及其他部门供素材 |
| 美编部 | 基础、复杂、大型设计及验收 | 处理内部、外部和教师需求 |
| 原创部 | 原创需求及例外工作记录 | 无明确默认费率部分走人工登记 |

### 现状业务

需求方在群里发信息，部长转述并私下安排，成员通过链接和文件交付，老师在不同群里提出修改。办公部周期性收集各部门表格，人工辨认参与人、重复行和不同工时口径。现状图用于说明改造前问题，不代表当前系统仍按此实现。

![现状推文协作](diagrams/current-business-sequence-publication.svg)

![现状统计](diagrams/current-business-sequence-accounting.svg)

主要问题是同一任务分散于多个群、意见与稿件版本难对应、完成后材料未集中归档、规则工时与人工核定缺乏解释。旧稿中“教师被简化”“部长承担老师二审”“办公按时段值班”等口径已由确认决定替代。

### 改进后的业务

推文以任务串起来源、采编内容审核、安排排版、运营内审、不同老师两审、发布和归档。两位指定运营部长均为审校岗位，任一确认即可送老师；老师审核记录保留但不计工时。退回后提交新排版版本，重新走完整排版审核链。

![改进推文业务](diagrams/improved-business-sequence-publication.svg)

采编与办公共用稿件站点行。创作和对接以每行为单位，各自贡献分开；可选内容老师先审内容，最终交付再由管理人员验收。只有正常归档稿件可关联推文，不把不同频率的采编、排版和周期统计强塞进一个不可拆分业务。

![改进采编办公](diagrams/improved-business-sequence-editorial.svg)

摄制按预约时间开放领取或由部长安排；美编与其他部门需求按目标部门承接、提交和验收。固定承接可选，取消后按部门队列轮转后续任务，手工安排可覆盖尚未交付的安排。轮转是任务顺序，不是某人负责某个时段。

![改进部门交付](diagrams/improved-business-sequence-jobs.svg)

正常完成自动归档并按规则只生成一次贡献；强制关闭保留原因，不自动计时。人工登记补充无法由明确默认规则计算的工作。报表通过筛选、列配置和视图保存提升灵活性；核定差异有逐次审计，期末封存后保留当时快照。

![改进统计结算](diagrams/improved-business-sequence-accounting.svg)

### 自动化与人工责任

系统自动推导状态、校验权限和阶段、归档、计时、生成提醒意图。部长负责安排、验收和合理例外；老师对内容与推文质量负责。尚未接入的群机器人与订阅消息保留为未来外部渠道，当前站内待办不能当作微信群送达证据。

## B 系统需求

## B 系统用例与参与者

![系统功能导航](diagrams/system-use-case-overview.svg)

软件边界包括网页、小程序和统一后端。使用者是访问软件的人；中心工作人员在业务组织内部，但在软件边界外，因此属于系统参与者。账号角色与业务岗位不是一一对应：不同任务可指定不同审校人。管理员替代办理范围以规约为准，不能代替指定老师。

一个用例可以关联多个参与者，这是合法UML。本稿按主要责任分区并在规约说明协同及授权替代，减少交叉线；不为减少线条伪造角色继承或删掉真实业务责任。四个详图的编号与规约完全一致。

### UC-AUTH-001：登录工作台

| 项目 | 规约 |
| --- | --- |
| 执行者 | 使用者；文中明确的管理替代者按服务端授权办理 |
| 触发事件 | 执行者希望登录工作台 |
| 前置条件 | 账号有效且启用 |
| 后置条件 | 网页或手机获得同一账号的权限范围 |
| 涉众利益 | 执行者获得明确回执；中心保留责任和业务证据；计酬成员的贡献可核验 |
| 字段列表 | 账号、密码 |

**基本路径**

1. 提交账号和密码。
2. 验证凭据和账号状态。
3. 建立有效会话并返回身份。
4. 展示身份允许的业务入口。

**扩展路径**：凭据错误拒绝；频繁失败限流；停用账号不得建立会话。

### 公共补充约束

所有授权以服务端会话为准。敏感写操作校验角色、部门、当前版本和阶段。失败不得形成部分归档。附件限制为单文件12 MiB且验证任务归属；外部用户只能取自己的附件。自动工时只面向有效内部计酬成员。

新版本保留历史审核和批注，重新进入适用审核链。备注与工时调整原因是不同字段；前者说明任务，后者逐次解释核定变动。封存保存当时结果。

### 路径评审规则

基本路径按业务意图描述，不以按钮或SQL作为用户目标。替代路径明确失败、退回及恢复位置；不同频率的业务通过独立任务及关联字段连接。自动归档与计时是完成行为的后置条件，不另画“系统”参与者。

#### 规范化与必要快照

部门、用户、任务、版本、审核、工时分别保存独立事实，避免名称和角色在每项任务中重复作为权威值。task_reviewers保存岗位安排，reviews保存实际审核；article_lines按稿件站点逐行计量。关联表使用复合键，版本和任务用复合外键防止跨任务误引用。

saved_views.config、outbox.payload与seal_rows.data使用JSONB表示用户视图、通知信封与不可变历史快照，是有明确生命周期的文档值，不代替核心实体关系。worklogs保留当时规则、倍率、费率与来源，属于有意保留的结算依据，不随政策变更回写。

#### 技术表与兼容边界

本地schema_migrations记录迁移执行，不算业务表。云端另外有_state、_requests、_uploads三个支持表，分别管理修订号、幂等请求和对象上传准备/回收；它们不是旧文档型数据库。

duty_slots仍留在迁移结构中，仅为兼容历史；当前代码不以时间段排班，实际使用duty_rotation和duty_rotation_members按先后任务轮转。file_payloads是测试及兼容载荷；云端正式附件在私有对象存储workbench-private，files只保存元数据与完整性哈希。

### D.2 业务层的精化

表示层只提交业务命令。app.js负责HTTP路由、会话、来源校验和输入错误映射；domain.js负责推文，jobs.js负责部门任务，reports.js负责工时与报表，annotations.js负责选区批注。配置、默认承接、轮转与通知各有独立模块。

发布与正常验收把完成事实、archives、worklogs、events及通知意图放在同一事务。唯一约束阻止重复贡献；失败整体回滚。强制关闭写原因且不生成自动工时。小时使用万分之一小时整数，金额使用分；创作者加急倍率与审校分摊分开计算，教师、外部和不符合计酬资格者排除。

云端cloud-db.js先用wb_snapshot读取一致快照，在一次性PGlite工作区运行现有SQL规则，产生变更集，再通过单次wb_command事务以修订号CAS、请求ID和摘要提交。工作区是可丢弃的请求计算材料，权威事实在云端。冲突返回明确失败，调用方刷新后再办，不以本地文件充当生产数据库。

服务端密钥保留在云托管；客户端不得直写业务表或自报角色。云schema对匿名及普通客户端角色撤销直接权限，核心业务只能走经认证的后端。小程序薄网关只允许固定上游和路径，不是第二业务后端。

### D.3 表示层的精化

网页提供登录前介绍、角色首页、按业务分区的任务、详情与版本、精细选区批注、报表列配置与封存、政策与默认承接配置。手机保留蓝色卡片和首页／协作广场／我的三底栏，提供轻量创建、领取、交付、审核、消息、个人记录和工时。

两端请求同一/api/v1契约；Web使用安全会话Cookie，小程序使用Bearer会话经网关转发。所有可见按钮只是提示，服务端再次授权；失败保留输入并解释权限、过期版本或状态冲突。复杂Excel和封存以Web为主，不在手机再造第二套逻辑。

附件上传先完成私有对象准备，再提交元数据，下载必须验权并检查长度与SHA256。批注只标工作台清洗后的预览或正文，不能声称直接在公众号线上页面修改。

### D.4 部署和运行边界

网页/API在CloudBase云托管运行，PG和私有对象存储均在云端，本机关闭不影响正常功能。站内消息已实现；群机器人、订阅消息和微信正式版发布尚未完成，不把outbox记录当成已送达群消息。旧接入环境的薄网关需在2026-12-11试用到期前续期或迁移，详见现有部署文档。
