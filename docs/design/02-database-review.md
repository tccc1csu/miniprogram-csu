# 数据库设计评审记录（不并入课程作业）

本轮数据库设计沿用已通过初步审阅的分析模型，不修改现有小程序集合，也不修缮 SRS／SDD／STD 框架。总图是唯一作业主图，八张分视图仅作为查阅字段关系的辅助材料。

## 课程对应

课件第 398 页：类、属性、对象到表、列、行；399 页：1NF／2NF／3NF；400 页：继承共享主键、一对多外键、组合外键非空、多对多中间表；402 页：稳定唯一标识；403 页：先规范化再讨论性能冗余。对应 PDF 与分析评审记录保持一致。分析类没有声明的继承关系不新增；可选计量扩展使用共享键，但明确其设计含义。

## 已确认与设计口径

已确认：两天加急阈值、1.5 倍、时间冲突拒绝；任务明细与成员周汇总均需要；办公部部长生成／导出中心周报；规则由会议确定、开发者维护。

沿用待确认事项：两天按 48 小时还是自然日、冲突资源范围、哪些贡献使用加急倍率、非运营稿件一审安排。参考 DDL 可保存未确认的日基准，但业务服务在口径明确前不能据此自动判断。

本轮计算约定：周一至周日，工作发生时刻确定工作周；基础工时精度 0.0001 小时，金额精度 0.01 元，逐条四舍五入后汇总。以上不是用户已确认的会议制度。规则按发生时刻还是核定时刻选版需业务核对；数据库保存实际选定规则版本，避免以后按最新规则重算历史。

单中心、成员一个当前部门及一个当前账号角色沿用现有分析；未扩展多中心租户或跨部门多职角色。通用流转的编排、部长确认和整体结束归集仍是拟开发建模方案。

## 2026-10-13 总图版式修订

参考用户提供的 Quickbooks 1.0 ERD 与 Shopify ERD 的表卡片、字段旁键标记、外键目标名和分区布局。仅借鉴图面表达，不迁移其业务结构。保留原47张基表、5个视图、85条真实外键及20个分析实体对应。

主图采用固定三列分区与两列区内紧凑排布；按用户后续修订，主键显示黄色钥匙、外键显示独立蓝色小箭头及目标表名。删除Type、Null、R编号、目标列与约束表达式的图面展示；完整信息保存在数据字典及关系清单。表外从99条线（85条外键及14条视图依赖）精简为21条关键真实外键，箭头指向被引用表，其他引用直接用字段旁的目标表名表达。扩展带位于区域边缘，不插入虚构业务表。

PlantUML继续作为完整关系模型源文件，受布局引擎限制，作业主图的精确排版由`render_database_overview.py`读取同一model-index.json生成，`rasterize_database_overview.cjs`将同一SVG转换为PNG。两个表示都按实际DDL核验；不能用默认PlantUML渲染结果覆盖最终紧凑图。

### 后续实现注意

归档与贡献登记、周报快照与封存、资源冲突检查与预约写入都必须是完整事务。SQLite 参考 DDL验证了部分跨行条件，不能替代服务端角色资格校验与生产数据库并发控制。时段冲突在资源范围未确定时不能擅自做成“所有摄制任务一律不能重叠”。

历史表采用不可改写策略；退回重提、稿件新版本与规则新版本已建模。已核定贡献冲销／更正、任务取消和重新分派如进入后续需求，应补充带审批依据的更正事件与状态迁移，不直接开放 UPDATE 绕过历史保护。本轮没有将这些未确认的新流程写进作业主路径。

现有微信文档数据库落地可以按聚合存储，但必须明确外键、复合唯一和跨文档事务在平台中的等价实现。不得把 SQLite DDL 当作已经执行的微信云数据库迁移。
